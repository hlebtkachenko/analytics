# Inbox UX rebuild on the Ramp Bill Pay pattern

Date: 2026-09-21. Branch `hlebtkachenko/inbox-ux`, stacked on
`hlebtkachenko/inbox-phase-1b-actions` (PR #72).

## Problem

The Phase 1b inbox pages project the data model onto the screen: hints,
provider, routing target, rule, correction and event each got a tile or a
column. Hleb reviewed the live demo on 2026-09-21 and could not see the path an
arrival takes. Concrete findings:

- `/inbox`: the drop zone owns the top third of the page; four filters, one of
  them a raw user id; two status-like columns (Status and State); ISO
  timestamps; a confidence percentage on images; internal type names; no counts
  and no grouping by "what needs me".
- `/inbox/[itemId]`: title "Item"; twenty inputs and eight buttons visible at
  once; Legal entity and Partner asked twice (hints and draft); two verbs
  (Process, Route) for one journey; raw ids for partner, document and user;
  engineer voice in the explanation; a history of codes; a 38-byte text file
  refused inline.
- `/inbox/settings`: routing targets as ten internal enum rows times eight
  columns; the storage quota shown to accountants.

Decisions taken with Hleb (2026-09-21): group the list with tabs; remove the
hints concept from the UI; mirror Ramp Bill Pay for the item page; keep the
settings, rules and channels pages as they are and only analyse them here.

## Scope

In: `/inbox` and `/inbox/[itemId]` rebuilt; additive API fields and one list
query parameter; one members list BFF route; labels; the operational proof
updated; the analysis of the settings page in this document.

Out: schema changes; AI or ISDOC extraction; amounts in the list (no provider
extracts them yet); an invoice line editor in the inbox (invoice kinds are filed
after the ISDOC parser, as in Phase 1b); the settings, rules and channels pages;
the documents pages; new dependencies.

Named cuts against today's pages: the Assignee column of the grid (the assignee
stays on the item and in the filter); the hints tile; the confidence, detected
type and state columns.

Every capability of the current pages survives: upload, filters, bulk approve,
bulk discard, bulk assign, route to document with corrections and reasons,
duplicate acknowledgement, reference conflict versioning, attach to an existing
document, discard with reason, restore, assign, snooze, clear snooze, reopen,
process a held item, re-split a failed parent, create a rule from an item. The
executor lists them from the current pages before writing the new ones.

## Design

### Reference

Ramp Bill Pay (from Hleb's reference screenshots): a left list grouped by state
with search and Prev K / Next J; a centre pane titled by the vendor and invoice
number with Overview and Activity tabs, sections that carry a "Complete" or
"Missing" chip, and a "Ready to approve" panel listing plain-sentence checks; a
right pane with the original document and zoom; a bottom bar with Save draft, an
overflow menu, and one primary button.

BAP keeps its Carbon vocabulary (`@bap/design-system`, `PageContainer`,
`DataGrid`, `Tabs`, `Modal`, `OverflowMenu`, `Tag`, `ContainedList`) and the
product shell. Only the information architecture is borrowed.

### `/inbox`

- Header row: title "Inbox", the organization switcher as a compact inline
  dropdown, a primary "Upload" button (file input, multiple), and an overflow
  menu with Sources (`/inbox/channels`), Rules, Settings. No permanent drop box.
  The whole page accepts drag and drop through an overlay that reads "Drop files
  to upload"; the 25 MB rule appears only as a refusal message.
- Tabs, each with a count: To review · Filed · Discarded · All. To review is
  every item that waits for a person: `needs_review`, `received`, `failed` and
  `processing`, minus items snoozed into the future (the list query parameter
  `snoozed=exclude`). Filed is `routed`. Discarded is `discarded`. All is every
  item. Snoozed items appear in All only, with the status word "Snoozed". The
  tab is a query parameter so links and reloads keep it.
- Counts come from the list response (`counts`, see API), computed under the
  caller's scope but ignoring the status, issue and assignee filters, so a tab
  shows its number before it is opened.
- Grid (the `DataGrid` block) columns: Item (an icon by payload kind and
  detected type, then the primary filename, or the sender for email items, and
  "+N files" when more than one), Received (local date and time, `cs-CZ`
  formatting through `Intl`), Source (Upload, Email, API, with the origin as
  secondary text), Legal entity (name resolved from the entities list, "Not set"
  otherwise), Status (one word: Needs review, Held, Processing, Failed, Filed,
  Discarded, Snoozed), Decided by (only meaningful on Filed and Discarded: the
  person's name, "Rule: name", "Default", "Channel default"), and a row action
  "Review" (To review) or "Open" (other tabs). Confidence, Detected type and
  State are gone from the grid; the detected type is the icon's tooltip.
- Filters (Issue, Confidence band, Assignee as a member picker with an
  "Unassigned" entry for the literal `none`) hide behind a "Filter" toolbar
  button; active filters show as removable tags. The query parameters stay as
  they are.
- Bulk actions stay, all four: select rows, then Approve, Discard, Assign,
  Snooze in the batch bar. Assign opens a member picker, never a text field.

### `/inbox/[itemId]`

Two panes on the Carbon grid, nested `Grid` inside `PageContainer` as today. At
`lg` (16 columns): centre 9, original 7. At `md` (8 columns): 4 and 4. At `sm`:
stacked, original first. No list rail (the expanded product rail leaves about
770 px at 1056; a third pane does not fit).

- Prev and Next in the bottom bar walk the tab the user came from (query
  parameter `tab`, default To review): the page reads the first page of that
  tab's list and finds its neighbours. K and J trigger them when focus is
  outside an input and no Modal is open.
- Header: the primary filename or sender as the title; below it one line
  "Received 20. 9. 2026 22:49 · Upload by Hleb Tkachenko" (or "Email from
  sender", "API channel name"); the status as a tag.
- Centre tabs: Overview, Activity (with the event count).
- Overview, top panel, in one of three voices:
  - "Ready to file": every required field present, no open issue. Lists the
    checks that passed as sentences: "Goes to Documents as Other for Henderson
    (default for PDF)", "No earlier copy of this file", "Legal entity set by
    rule Fio statements".
  - "Needs your input": lists what is missing or open, one sentence each:
    "Choose the legal entity", "Probable duplicate of INV-2026-0009, review or
    acknowledge", "Reference FA-2026-12 already exists, file as a new version or
    change it".
  - "Filed" or "Discarded": one sentence with the destination link and who did
    it, keyed on `decidedByKind`: "Filed by rule Fio statements", "Filed by Hleb
    Tkachenko", "Filed by the default for PDF", "Filed by the channel default";
    an auto-routed event carries the rule author's id, so the person's name is
    never used for a rule decision. The form below is read only. The sentences
    come from the extraction reasons and issues, the routing target,
    `duplicateOfItemId` ("Exact copy of <link>"), and the corrections. Probable
    duplicates and reference conflicts stay where they are today: the route
    answer raises the Modal with the candidates and the choices (acknowledge,
    file as a new version, change the reference); the panel only states them.
    For invoice kinds the panel says that invoices are filed after the ISDOC
    parser lands and offers Attach to an existing document; the primary button
    is disabled. Codes never reach the screen; every code maps to a label in
    `resources.ts`.
- Overview sections, each with a "Complete" or "Missing" chip. A "Defaults" chip
  marks a section whose values came from rule or channel defaults rather than a
  person, so "Complete" stays honest.
  - Where: Legal entity (dropdown by name), Kind (dropdown by label).
  - Document: Title, Document date, Reference, Currency, Partner (a search
    picker by name over the partners BFF, with "Create partner" as in
    `/documents/new`).
  - Changing a prefilled field reveals an optional one-line "Why" input beneath
    it; the answer travels as a correction reason exactly as today. Where the
    value came from is one line in the top panel, not per field.
- Hints: no tile. The item's hint values prefill the draft. `hint_text` shows as
  a read-only "Note" line in the header when present. The hints write route
  stays in the BFF and the client for the channels that set hints; the page no
  longer calls it.
- Activity tab: a `ContainedList` of sentences, newest first, each with the
  actor's name and the local time: "Filed to DEMO-2026-0002 by Hleb Tkachenko",
  "Rule Fio statements matched", "Received through the email channel
  invoices@bap.invalid", "Discarded as duplicate by Owner". Actor names resolve
  in the page from the members list: a member's name, "A former member" when the
  id is not in the list, "Channel" plus the origin for a `channel_` id,
  "Automation" for a null actor. The `routed` event of an auto-route carries the
  rule author's id; the sentence uses the rule name from `decidedByKind` and
  `decidedByRuleName` instead. Corrections appear in the same list ("Legal
  entity changed from Henderson to Profese: wrong default").
- Original pane: PDF in the same `<iframe>` as today (no `sandbox`; the Chromium
  PDF viewer needs it off, see the current page and the blob controller), images
  as `<img>`, `text/*` and CSV fetched and shown in a `<pre>` up to 64 KB
  (`INLINE_MEDIA_TYPES` in the web contract extended), anything else as a
  download card. A file switcher when the item has several files. No email tab;
  the sender is in the header.
- Bottom bar (sticky inside the centre pane): Prev, Next, an overflow menu, and
  one primary button. The overflow holds Discard, Snooze, Assign, Attach to an
  existing document, Create a rule from this item, Re-check, and, where the
  status allows, Restore, Reopen, Clear snooze, Re-split. Each opens a Carbon
  `Modal` with the fields of today's tiles (discard reason, member picker, date
  and time, document picker). Every verb maps to an existing client call: Reopen
  = `route/undo`, Re-check and Re-split = `process`, Clear snooze = `snooze`
  with null, Restore = today's restore call. The primary button follows the
  status: `received` "Process", `needs_review` "File as document", `routed`
  "Open document" (a link), `discarded` "Restore", `failed` "Re-check". The bar
  and the overflow render only for `manageDocuments`; other members see the page
  read only, as today.
- Nothing on the page shows a raw id, a status code, an event code or an ISO
  timestamp.

### API and BFF additions (additive, no schema change)

- `GET .../inbox/items` gains the query parameter `snoozed=exclude` (drops rows
  with `snoozed_until > now()`) and its response gains
  `counts: { toReview, filed, discarded, all }`, computed in the same repository
  call under the caller's scope predicate, ignoring the status, issue and
  assignee filters, with one grouped count. The list entry gains `sender`
  (already a column on the item) and `decidedByRuleName` (left join on
  `app.inbox_rule`).
- The item detail gains `decidedByRuleName` (nullable). Events keep
  `actorUserId` only: `bap_api` has no SELECT on `auth."user"`, so names are
  resolved in the page from the members list.
- New BFF route
  `GET /api/bff/application/organizations/[organizationId]/members` returning
  `{ members: [{ id, name, email }] }` from the Better Auth organization member
  list, for the assignee pickers and the activity names. It reads Better Auth
  directly, like the members page; `docs/product-pages.md` names it as the
  documented exception.
- `apps/web/src/lib/inbox/contract.ts` mirrors the API changes exactly; the
  parity test covers them.

### Labels

Every new string lives in `apps/web/src/i18n/resources.ts`. Statuses, decided by
kinds, event kinds, issue codes, discard reasons and provider steps each map to
a sentence or a word; the executor extends the existing label maps in
`apps/web/src/lib/inbox/labels.ts`.

### Settings, rules and channels: analysis only

Kept unchanged in this PR. Findings for a later decision:

- The routing targets table shows ten detected types the organization never
  chose, eight columns wide, mostly "Never", "n/a", "None", "Platform default".
  An accountant reads it as configuration of a machine, not as their rules.
- The same information reads as sentences: "A PDF goes to Documents as Other for
  Henderson; a person confirms every one." One row per detected type, the
  overrides first, the platform defaults collapsed under "Defaults".
- Rules and routing targets answer one question ("where does this go") on two
  pages with two vocabularies. One "Rules" page with two sections, "Your rules"
  (ordered, editable) and "Defaults by file type" (the targets), removes the
  split.
- The storage quota belongs to the organization settings page, next to the
  member and entity administration, not to the inbox.
- Channels reads well enough; renaming the destination "Sources" in the menu is
  the only change the list page makes.

Recommendation: one later PR that folds the targets into the rules page as
sentences and moves the quota. Hleb decides after this PR is live.

## Security

No new write path. The counts, `sender` and `decidedByRuleName` fields expose
nothing the caller could not already read on the detail route under the same
tenant predicate and entity scope. The members BFF route returns only id, name
and email of members of the caller's own organization, which entity-scoped
members already see on the members page. Blob previews use the existing blob
route and its scan status gate with today's `<iframe>` rule.

## Review round 3 (Hleb, 2026-09-21 15:30)

Finding: the upload path (primary button with a hidden input, page-wide overlay,
one summary notification) is not the Carbon pattern; Hleb's reference is
carbondesignsystem.com/components/file-uploader/usage/ and /style/ (an "Upload
files" heading, a sentence, a dashed drop container "Drag and drop files here or
click to upload", then one row per file with an × to remove).

Decisions:

- The header "Upload" button opens a passive Carbon Modal "Upload files": one
  sentence naming the accepted types and that each file becomes an inbox item; a
  `FileUploaderDropContainer` (multiple, the same accepted types); one
  `FileUploaderItem` per file: uploading while the request runs, complete when
  accepted, edit + invalid with the refusal sentence when refused; × removes the
  row only. Files upload as soon as they are added, one request per file; the
  list refreshes and the New tags appear as before.
- Dropping files anywhere on the page keeps the overlay as feedback and opens
  the same modal with the dropped files.
- The summary notification and the hidden input go away.
- The inbox proof step that drops two files asserts the modal items and then the
  rows.
