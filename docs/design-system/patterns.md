# Carbon Patterns

The complete offline pattern guide is
[Carbon Core patterns](knowledge-base/06-patterns.md). It covers all 18 pinned
website pattern pages with a runnable neutral-composition expectation or a
documentation-only reason. This page remains a short routing summary.

## Approved Carbon references

- Common actions: use the same action placement and labels for equivalent work.
- Dialogs: ask for focused input or communicate urgent workflow information.
- Disabled states: remove an action only when it cannot be performed.
- Disclosures: reveal secondary detail progressively.
- Empty states: explain the current absence and the next meaningful action.
- Filtering: use controls that make active criteria clear and reversible.
- Fluid styles: use one coherent fluid-control treatment within a form group.
- Forms: group related fields, provide labels and validation at the boundary.
- Global header: combine UI Shell only after navigation requirements exist.
- Loading: communicate work in progress without masking a stable state.
- Login: defer until the chosen authentication system and requirements exist.
- Notifications: communicate system feedback with the Carbon notification API.
- Overflow content: prefer reflow or accessible disclosure before clipping.
- Read-only inputs: show a value as immutable without making it look editable.
- Search: expose an intentional discovery flow, not an unscoped input.
- Status indicators: combine text or shape with color.
- Text toolbar: use only when an editor has defined commands and selection.

The source directory also contains its overview page, bringing the exact closed
world to 18. The [website coverage artifact](knowledge-base/coverage-website.md)
records each path, status, unique anchor, local target, and reason.

## Data visualization patterns

Use a chart only when it answers a defined question. Give it a descriptive
title, meaningful axis labels, a stable color mapping, and an equivalent table.
Start comparison and part-to-whole axes at zero. Do not use a legend when direct
labels work, and never make color the sole means of distinction.

For dashboards, do not introduce product dashboards in this phase. Future views
should preserve chart spacing, legend placement, units, localization, and
interactions across related visualizations.

Use the dedicated
[data-visualization chapter](knowledge-base/08-data-visualization.md) for chart
selection, anatomy, axes, legends, palettes, options, accessibility, and network
diagrams.
